# Changelog

## 1.12.0 - 2026-11-24

- **Standalone app**: **Clone Repository** clones a repository from the app, as TortoiseGit's **Git Clone** does. Its dialog takes the URL (or a folder to clone from) and the folder to clone into, which is named after the repository until you change it, a branch, and the options of `git clone` as switches: **Clone submodules** (on), **Shallow clone** with its count of commits, and under **Advanced** the remote's name, **Bare repository** and **No checkout**. It starts with the URL of a repository on the clipboard, shows the command it runs, how far git is while it clones, with **Stop** to end it (what was cloned so far is removed), and what git said when a clone fails. The clone opens in a tab. Open it from **File > Clone Repository**, the start screen, the **New Tab** dialog, or the file manager: right-click a folder and choose **Sidereal > Clone...** (`sidereal --clone <folder>` in a terminal). The Windows installer adds the menu item; on macOS and Linux, choose **File > Install Finder Quick Actions** or **Install File Manager Menu** again to get it.
- Hide the field filtering the commits and **Jump** from the bar above the graph if you don't use them: the standalone app's **Toolbar** settings (**Toolbar Buttons** before) list **Filter field** and **Jump** below your own buttons, each with a switch, and VS Code has `sidereal.toolbar.controls`. The **Filter Commits** button still filters, Ctrl+F (Cmd+F on macOS) opens its form with the field hidden, and Jump's keyboard shortcuts still work.
- The menu of the **Working tree changes** row offers more, as TortoiseGit's log does: **Stash Pop...** while there is a stash, **Pull...** and **Fetch** (saying when the repository last fetched) for a repository with a remote, and **Update Submodules...** for one with submodules. They do what the toolbar's buttons and the **...** menu do, and show also when there are no changes. **Commit...** now comes first.
- Push, Pull and Fetch run from the keyboard while a commit's details are open. Their keys (Ctrl+Up, Ctrl+Down and Ctrl+Shift+Down) used to follow the graph to the commit's child or parent instead whenever the details were open, which they are after any click on a commit, so the shortcuts the buttons name seemed to do nothing. Following the graph now has keys of its own: Cmd+Up and Cmd+Down on macOS, as before, with Shift for another child or parent, and Alt+Shift+Up and Alt+Shift+Down on Windows and Linux, with Alt+Shift+Page Up and Alt+Shift+Page Down for another child or parent. Ctrl+Up and Ctrl+Down no longer follow the graph, on macOS either. The standalone app's **Keyboard Shortcuts** settings list the four under **Commit Details**, where you can change them, and now tell when a key recorded for the graph is one of the details view's, or the other way around.
- **Standalone app**: a click on the active tab leaves the keyboard with its page. Before, the tab strip kept it, and the graph's shortcuts did nothing until the next click in the page.
- A commit that five or more branches of the remotes sit on shows three of their labels and folds the rest into a `+N` badge after them, drawn as a remote branch label; click it to unfold them, and again to fold them. The three shown are the ones you most likely look for: the upstream of the checked out branch, the upstreams of your other local branches, then the remote's default branch.
- The commit details view opens below the graph by default, where it used to dock on the right in a window wider than tall. Drag its title bar to the right to dock it there, or choose **Dock Details Right** or **Dock Details by Window Shape** in its menu or the **View** menu; where you leave it is remembered.
- **Standalone app**, macOS: a tooltip shows half a second after the pointer rests on something, as on Windows and Linux. Before, the first one took a second and a half, which showed most in the **Repo** dropdown, where the next rows' tooltips then came at once. A delay you set yourself with `defaults write` (`NSInitialToolTipDelay`) is kept.
- A submodule among the uncommitted changes that isn't as the repository records it says what to do about it. Select its row and the diff pane heads the two `Subproject commit` lines with a note: how far the commit checked out is from the recorded one and whether the submodule has changes of its own, then what to do, with **Update Submodule...** to check the recorded commit out again and **Open Submodule** to commit or discard its changes there. The row's tooltip says the same.
- The commit form warns before a commit moves a submodule back. A submodule left on an older commit, by a pull or a checkout that moved the recorded one on, used to go into the next commit unnoticed when it was staged with everything else, taking the commits it was behind out again. Now the form says `This commit moves vendor/lib back 7 commits.` below its buttons while such a change is staged, with **Unstage** to take it out.
- A submodule whose only difference is its own uncommitted or untracked files has no **Stage** button, and **Stage All** leaves it out: staging records the commit a submodule is at, never its files, so the button did nothing. When such submodules are all there is, the commit form says that their changes are committed in the submodule itself, with **Open Submodule**, where it said to stage the changes.
- A staged change of a submodule shows what is staged: the commit the index records, without the `modified content` and `untracked content` of its working tree, which no commit of this repository takes. Those stay on its row under **Changes**.
- The **Update Submodules** dialog marks a submodule that has changes of its own with **Has Changes**, as an update may stop at them. When it does, the failure says what to do besides what git said: open the submodule to commit or stash them, or update with **Force** to throw them away.
- The form dialogs have a new look: **Push**, **Add Remote** and **Edit Remote**, **Create Worktree**, **Add Custom Button**, **Edit Commit Message** and **Label Colors**, as **Update Submodules**. What a dialog does is in fainter text under its heading, the buttons are in a bar along its bottom, **Cancel** then the action at the right, and the corners are rounder. In the first four, each check box is a switch at the right of its row, the options that belong together are in a card, a git flag shows as a chip after its option, and **Advanced** is a card that opens.
- A file leaves the uncommitted changes as soon as **Revert...** or **Delete...** has thrown it away, instead of once the view has read the working tree again, which takes a while in a large one. An added or renamed file that was reverted becomes an untracked file, and moves to **Untracked Files** once the view has reloaded, as before.
- The uncommitted changes show sooner after **Stage**, **Unstage**, **Revert...**, **Delete...** and **Add to .gitignore**, of files and of hunks, which shows most in a large working tree. These change nothing but files, so the view no longer reads the branches, remotes, stashes and worktrees again before it reads the changes, and it reads the working tree's status once where it read it twice.
- **Standalone app**: several windows. Drag a tab out of its window and let go to give it a window of its own there, or choose **Move to New Window** in the tab's menu (**Window > Move Tab to New Window** for the active tab). Drag a tab onto another window's tabs or graph to move it there. The tab keeps what it shows and what it is doing, such as a commit's details or a fetch under way; a window whose last tab moved away closes. **File > New Window** (Ctrl+Shift+N, Cmd+Shift+N on macOS) opens an empty window. Opening a repository that another window shows brings that window to the front, as does asking for **Settings** while it is open in another window or tab.
- **Standalone app**, macOS: a click in a Sidereal window that isn't the active one reaches what is clicked, as on Windows and Linux, so a tab of another window can be dragged at once. Before, the first click only brought the window forward, and pressing one of its tabs moved the window.
- **Standalone app**: the windows open again where they were, at their size, when the app next starts: every window open when you quit, or the last one you closed. Before, the window always opened at one size in the middle of the screen.
- While an AI agent resolves conflicts with **Resolve with AI**, Sidereal no longer waits for it: **Resolved**, **Resolve Using Ours** and **Theirs**, **Fetch** and every other action run at once, where before each waited behind the agent, sometimes for minutes. The files the agent was given stay its own until it is done, and a file you settle elsewhere meanwhile is left as you left it. **Skip**, **Abort** and a reset stop the agent first, as do closing the tab and quitting.
- Several AI agents can resolve conflicts at once: **Resolve with AI** on a conflicted file starts beside another file's agent, up to three in a repository, each with its own progress notice and **Cancel**. An agent given every conflicted file still works alone. Runs that end close together share one summary, which waits for a dialog you have open.
- **Resolve 3 Files with AI...** in the menu of several selected conflicted files hands just those to one agent.
- A conflict marker (`<<<<<<<` or `>>>>>>>`) no longer goes into a commit unnoticed: **Commit**, an operation's **Continue** and **Resolved** ask first, and **Resolve with AI** carrying an operation through stops before it continues. A file **Resolve with AI** couldn't read stays conflicted, where before it was taken for deleted and staged as it was, markers and all.
- **Standalone app**: the **Repo** dropdown lists the submodules of the repository you are looking at, also those never opened, and theirs, so that any of them is a click away. It has two parts: **This Repository**, with the repository, its worktrees and its checked out submodules, and **Recent**, with the other repositories opened lately. A submodule or worktree lists the same as its repository does, so one submodule's tab reaches the others. Before, the dropdown listed a submodule only once it had been opened, among the recent repositories, and listed the worktrees and opened submodules of every recent repository; those of another repository are now chosen from that repository. A submodule that isn't checked out isn't listed.
- The **Repo** dropdown shows what each entry is with an icon: a repository, a worktree or a submodule, the icons the graph and the tabs show for them.
- **Standalone app**: opening a repository's submodules and worktrees no longer has other repositories forgotten from **File > Open Recent**: the last ten of them are remembered besides the last ten other repositories.
- **Update Submodules...** in the graph's **...** menu, and **Update Submodule...** on a changed submodule's row, open one dialog that lists every submodule of the repository to choose which to update, as TortoiseGit's does. The list sits beside the options, as tall as they are, so the dialog itself doesn't scroll (in a narrow window it stays above them); the options are switches, a row each. Each submodule is listed with its state (**Not Initialized**, **Out of Date**, **Conflicted**). The dialog's foot shows the `git submodule update` command the options come to, naming the submodules when only some are checked, and its button counts the submodules checked (**Update 3 Submodules**). All are checked at first, or from a row only that one, and **Select all** checks or unchecks them all. The options are in the same dialog, and **Advanced** adds **Merging** or **Rebasing** onto the commit instead of checking it out (`--merge`, `--rebase`) and **No Fetch** (`--no-fetch`). The options are remembered for next time. Before, the graph's **Update Submodules...** always updated every submodule. In VS Code, the References view's **Submodules** show their new state once the graph updated them, where before they kept the old one until refreshed.
- **Standalone app**: a submodule's tab no longer lists the submodule a second time in the **Repo** dropdown, named after its folder alone, which opened its Git directory (`.git/modules/...` in the parent repository) where nothing is checked out. Git names that directory as the submodule's main worktree; Sidereal now takes the folder the submodule is checked out in.
- A worktree removed in VS Code no longer comes back in the **Repo** dropdown now and then. Removed just as Sidereal was following the repositories the Git extension has open, which still lists a removed worktree, it was tracked again though its folder was gone.

## 1.11.0 - 2026-11-20

- With **Force push** ticked, the **Push** dialog says what the push overwrites: `Overwrites 2 commits on origin/main that main doesn't have.`, counting the commits the remote branch has, as last fetched, and the branch you push lacks. It says nothing when the push overwrites none, or creates the branch.
- Sidereal says when the repository last fetched, since what it shows of a remote is as of then: **Last fetched 3 hours ago** in the **Pull** button's tooltip and beside **Fetch** in its menu, at the foot of the **Push** dialog's list of remote branches, and in **Force push**'s description, whose lease holds against what that fetch saw. A repository that never fetched says nothing.
- **Open on GitHub** in the menu of a commit, of a branch label and of a file in a commit's details opens that commit, branch or file on the site the remote's URL points to. It names the site it opens (**Open on GitLab**, **Bitbucket**, **Azure DevOps**, **Codeberg**, **Gitea** or **Forgejo**) and shows only for a remote on one of them; a company's own GitHub or GitLab is known by its host name, such as `gitlab.example.com`. A local branch opens its upstream. For a commit the remote doesn't have yet, Sidereal says so instead of opening a page that isn't there. The address is built from the remote's URL: Sidereal itself still makes no network request.
- When a push is answered with a link to open a pull request for the branch, as GitHub, Bitbucket and Gitea answer a new branch (GitLab with a merge request), a notice at the foot of the view says where the branch was pushed, with **Create Pull Request** to open the link in the browser, or **View Pull Request** for a branch that has one. The notice leaves by itself after a while. It shows for **Push** and for a **Commit & Push** that pushes without asking. Before, the link was only in the output of a `git push` run in a terminal.
- The **Pull** and **Push** buttons count the commits the checked out branch is behind and ahead of its upstream, as `↓2` and `↑3` beside their labels, and their tooltips name the upstream. A branch level with its upstream, or without one, shows no count. The commits to pull are as of the last fetch. The counts are those the branch labels show, so turning off `sidereal.referenceLabels.showAheadBehind` hides them too.
- The bar above the graph takes one line where it took two or three. The **Repo** and **Branches** dropdowns are as wide as the name they show, instead of the longest name in their list; the list still opens wide enough for every name, as far as the graph reaches. Where the bar still has too little room, such as with the details docked right of the graph, it shortens its controls a step at a time until they fit on the line: the **Repo:** and **Branches:** labels become icons and **Jump:** goes, then the Git buttons show only their icons, then the empty **Filter messages** field folds away to its search button, which opens it, as Ctrl+F (Cmd+F on macOS) does. A bar that needs two lines either way keeps its controls whole. The fetch button at the bar's right end, which does what **Fetch all** in the **Pull** button's menu does, now shows only where the **Pull** button can't stand in for it: when the settings hide it, or while HEAD is detached (as in a submodule), where it can't pull.
- The **Push** dialog's **Remote branch** field lists the branches the remote has, to choose one instead of typing its name: click the field or its arrow, or press the Down arrow key. Typing narrows the list to the branches containing the text, those starting with it first; a click takes a branch, or the arrow keys and Enter. A name no branch has is still pushed as typed, and the field says below it that the push creates a new branch. With several remotes, the list follows the remote chosen. It lists a remote's branches whatever the graph shows of them: also with **Show Remote Branches** off, and for a remote hidden from the graph.
- **Standalone app**: Settings saves each change as you make it, so there is no **Save** to click: the theme, colors, shortcuts and AI settings apply at once, and what the graph is drawn with, or a changed Git executable, once you close it with **Done**. A value with a problem isn't saved until it is fixed, which closing Settings says first.
- The commands Sidereal runs Claude Code, Codex and GitHub Copilot CLI with can be changed, for when an agent's update changes its options before Sidereal follows: as text fields with **Restore Default** under the chosen agent in the app's **Settings > AI Features**, and as `sidereal.ai.claude.editCommand`, `sidereal.ai.claude.readOnlyCommand` (and the same for `codex` and `copilot`) in VS Code's user settings. A command left alone follows Sidereal's updates; a changed one runs as it is, without a shell. On Windows, an agent npm installed (started through its `.cmd` file, and so through `cmd.exe`) takes no `%` in a changed command, which `cmd.exe` would read as part of a variable: Sidereal says so instead of running it.
- **Standalone app**: Settings shows the settings another one brings up set in below it along a line, such as the chosen AI agent's commands or the **Custom** label colors.
- **Standalone app**: the **Feedback** section of Settings takes images. Paste a screenshot from the clipboard, or choose files with **Attach Image...**: up to four PNG, JPEG, GIF or WebP images go with the report, each shown small with a button to remove it. A picture larger than 2 MB is made smaller before it is sent; an animation that large is turned down.
- A submodule's graph labels the commit its parent repository records for it, as TortoiseGit's log does with `super-project-pointer`: a dashed label named after the parent, such as `app pointer`, on the commit **Update Submodule...** checks out, which shows how far the submodule's branches are from it. The label follows what is staged in the parent, and with every branch shown its commit has a row even when no branch reaches it. While the submodule is conflicted in the parent, both sides are labeled, `app pointer (ours)` and `app pointer (theirs)`.
- Choosing the branches to show, in the **Branches** list or with **All Branches**, clears a filter's **Range**, and the graph shows those branches. Before, the choice changed nothing while a range was filtered: a submodule opened from its row in the parent's changed files, which shows only the commits the change moved it across, kept showing just those commits whatever the branches chosen. The rest of the filter stays.
- **Standalone app**: a submodule's tab shows its parent repository's color, so that the tabs of a repository and its submodules read as one. A color picked for the parent shows on both; **Color** in the submodule's tab menu picks one of its own, and **Reset Color** gives it the parent's again.
- **Duplicate Tab** opens another tab of the repository you are looking at, to see two places of its history at once: keep one tab on an older commit while the other shows the newest ones. It is in the graph's **...** menu; in the standalone app also in a tab's right-click menu and the **File** menu, and in VS Code also in the Command Palette as **Sidereal: Duplicate Tab**. Each tab has its own commit open, scroll position and filters. In the standalone app the tabs of one repository share its name and color, the later ones numbered (`app (2)`), and the app starts again with one tab per repository. In the standalone app, choosing a repository that is open in a tab (marked **Open**) in the **New Tab** dialog opens another tab of it too. Any other way of opening a repository that has a tab still shows that tab, the one last used when it has several. Before, a repository could only have one tab.
- **Update Submodules...** in the graph's **...** menu updates every submodule the repository has, also one that isn't cloned yet, with the same options as a single submodule's **Update Submodule...** (**Initialize**, **Recursive**, **Update from Remote**, **Force**). Before, the standalone app could only update a submodule that showed among the uncommitted changes, and in VS Code only the References view updated them all.
- **Commit & Push** asks where to push once it has committed, in the **Push** dialog, which names the branch and the remote branch it pushes to, with **Set upstream** and **Force push** as for any push. Cancel it and the commit stays, unpushed. Before, it pushed to the branch's upstream without asking, and asked only for a branch that had none, so a commit could go to a shared branch by accident. To push without the question again, turn off **Ask where to push after Commit & Push commits** under **Graph** in the standalone app's Settings, or `sidereal.commitForm.confirmPush` in VS Code.
- **Standalone app**: **Help > Tutorials** opens Sidereal's [tutorial videos](https://zacheryglass.com/sidereal/tutorials/) in the browser: short narrated videos of the app, one feature at a time. The **About** section of Settings links to them too.
- **Standalone app**: when your diff tool doesn't open, Sidereal says why and offers **Choose Diff Tool**, which then shows the diff in the tool you pick. Before, **Open in Diff Tool**, a double click on a file and **Launch External Directory Diff** did nothing when the tool failed at once, as FileMerge (`opendiff`) does on a Mac without Xcode, or when Git's diff tool runs in a terminal, such as vimdiff. When Git's difftool has nothing to show, as for **Compare with Working Tree in Diff Tool** on a file that hasn't changed since, or a directory diff of only untracked files, Sidereal says so too (the tools it starts itself, such as Beyond Compare, show the two files the same). **Open Recent** on a repository that moved or is gone, a **Help** item whose file can't open, and an **Open files with** command that fails after it started now say so instead of doing nothing. In VS Code and the app, the diff tools to choose from leave out FileMerge when Xcode isn't installed, choosing one for **Launch External Directory Diff** then opens it, and VS Code's directory diff shows a tool's failure that Git hid.
- The standalone app's diff pane stages one hunk at a time. For a file of **Changes**, each hunk has **Stage Hunk** and **Revert Hunk...** at the end of its header: the first stages that hunk alone, leaving the file's other changes unstaged, and the second throws it away in the working tree after asking. For a file of **Staged Changes**, each hunk has **Unstage Hunk**. A hunk is applied only while the file still has it as shown; if the file changed since, nothing is touched and a message says so. Once a file's last hunk is staged, the next file of the list shows. A hunk's header stays at the top of the pane while its lines scroll past, so its buttons are in reach from anywhere in a long hunk, and the hunk that takes a staged one's place then shows from its header. The pane's header says which of the file's changes show, **Unstaged** or **Staged**, and for a file staged in part switches between the two; the pane stays with the unstaged changes as you stage one hunk after another. Click in the diff, or reach it with Tab, and the keyboard works there: J and K move to the next and the previous hunk, S stages the hunk the keyboard is on (marked at its left), U unstages it and R reverts it after asking, and the arrow keys scroll the diff instead of moving between the commits. The standalone app's **Keyboard Shortcuts** settings list these keys under **Diff Pane**, where you can change them. The second click of a double click on a hunk's button does nothing, so it can't act on the hunk that moved under the pointer, and while **Revert Hunk...** asks, the hunk it would throw away is framed. Before, only whole files could be staged, unstaged or reverted.
- The changed files of a commit's details and of the commit form work from the keyboard. Click a file, or reach the list with Tab, and the arrow keys move between the files instead of the commits: Shift+Up and Shift+Down select more or fewer, Home, End, Page Up and Page Down go further, and Ctrl+A (Cmd+A on macOS) selects them all. Enter opens the selected files' diff, as a click or a double click does, and Shift+F10 or the menu key shows their menu. In the commit form, Space stages the selected files (in **Staged Changes**, unstages them) and moves on to the next file, so that Space pressed again and again stages one file after another; Delete or Backspace reverts them, or deletes untracked files, after asking. Clicking a commit gives the arrow keys back to the graph. The standalone app's **Keyboard Shortcuts** settings list these keys under **Changed Files**.
- Right-click a file of the working tree changes for what before took its row's buttons, or wasn't there: **Stage** or **Unstage**; **Delete...** on an untracked file, which moves it to the Trash (the Recycle Bin on Windows) after asking, where before only **Clean up...** removed untracked files (in a VS Code remote window, which has no trash, the question says the file is deleted for good; where the trash doesn't take a file, such as on a volume without one, a second question asks whether to delete it permanently); and **Add to .gitignore...**, which asks whether to ignore the file, every file with its extension, or its folder. With several files selected, the menu acts on them together: **Stage 3 Files**, **Unstage 2 Files**, **Revert 3 Files...** (asking once, and listing them), **Delete 2 Untracked Files...** and **Add 2 Untracked Files to .gitignore**. Before, the menu of several files only opened their diffs.
- The graph's **...** menu has **Add Remote...**, **Edit Remote...** and **Delete Remote...**. **Add Remote...** asks in one dialog for the name (starting as `origin` while no remote has it), the URL and, under **Advanced**, another URL to push to, and fetches from the remote once added unless you untick **Fetch from it once added**. **Edit Remote...** shows a remote's name and URLs to change, and **Delete Remote...** deletes one, with its remote-tracking branches, after asking; with several remotes, each asks which one. A name another remote has, or one Git rejects, is refused. Before, the standalone app had no way to add or change a remote, and in VS Code only the References view did.
- **Prune Worktrees...** shows in the menu of a branch, or of a worktree's label, whose worktree's folder no longer exists: after naming the worktrees whose folders are gone, it has Git forget them, which frees the branches they had checked out. Before, the menu's disabled items pointed to the References view to prune them, which the standalone app doesn't have.
- **Standalone app**: a worktree's menu no longer has **Open Worktree in New Window**, which opened a tab there, as **Open Worktree in Sidereal Tab** does, and **Open Worktree in Current Window** is named **Open Worktree in This Tab**, which is what it does in the app.
- **Standalone app**: right-clicking in a text field, such as the commit form's summary or a dialog's field, shows **Cut**, **Copy**, **Paste** and **Select All**, with the spelling suggestions for a misspelled word above them. Right-clicking selected text elsewhere, such as a commit's SHA-1 or its message in the details, shows **Copy**. Before, a right click there showed nothing.
- Ctrl+F (Cmd+F on macOS) moves the keyboard to the **Filter messages** field above the graph, its text selected, to type what to find. The standalone app's **Keyboard Shortcuts** settings list it as **Find Commits (Go to the Filter Field)**.
- **Reveal in Finder** (**Reveal in File Manager** on Windows and Linux) in a changed file's menu shows the file in the system's file manager, for the working tree's files, a commit's and a submodule's folder. Not in a VS Code remote window, whose files are on another machine.
- **Standalone app**: the commit details view has a diff pane, which shows the changes of the file you select (or of the first file, until you select one) without opening a diff tool: below the details and the files when the view is docked right of the graph, right of the file list in the **Changes** tab when it is docked below. Changed words are marked within a changed line, and a line whose line break alone changed names both (CRLF, LF). Its arrows step to the file above or below, and **Side by Side** shows the old lines beside the new ones. For the uncommitted changes it shows what is staged and what isn't apart (and so does **Open in Diff Tool** in a file's right-click menu: HEAD against the staged file, or the staged file against the one on disk, where a double click still compares HEAD with the file on disk), and an untracked file whole, follows a file as it changes, and keeps showing it as you stage or unstage it. **Show Diff** in the details view's title bar hides the pane or shows it again; docked right, its header collapses it. A file's right-click menu says which it opens: **Show in Diff Pane** shows the file there (showing the pane, or its tab, again if it was hidden or collapsed), **Open in Diff Tool** opens the same change in your diff tool, and the other items that open your diff tool name it too (**Compare with Working Tree in Diff Tool**, and **Open 3 Files in Diff Tool** for several selected files). A long diff shows its first 3,000 lines, with a button that opens the whole of it in your diff tool.
- Docked below the graph, the details view shows **Details** and **Files** as tabs of its title bar, each using the whole view, instead of side by side. In the standalone app the files' tab is named **Changes** and shows the diff of the file you select right of the file list, so you click through the files and read each one's changes without switching tabs; drag the line between the list and the diff to size them. It keeps the tab you chose, the arrow keys move between the tabs, and **Commit** shows the **Details** tab with the commit form. Docked right, the sections still sit one above the other.
- The commit form fills its **Details** section: the description grows into the room below it, so **Commit** sits at the section's foot instead of above an empty gap, and dragging the divider sizes the message. Docked below the graph, the form now fits without scrolling. The summary's length and **Write with AI** sit inside the summary field, in the commit form and in **Edit commit message...**'s dialog, and the length shows once you type.
- **Merge into...** and **Reset to this...** are planned in the graph, as a rebase, cherry pick or revert is, instead of a dialog and a prompt. A merge shows its merge commit on top of the checked out branch, or the branch moving as it fast-forwards, the same whether you choose it from a menu or drop a branch on the checked out one. Before, only the drop showed it, under the dialog. Its banner has **Create a merge commit** `--no-ff` (when it could fast-forward) and **Squash**, and **...** for **Don't commit** and the strategy, shown by their flags once chosen. **Edit Message** opens the merge commit's message below its row. A reset moves the branch's label to the commit and fades the commits only the branch had, with **Soft**, **Mixed** and **Hard** in the banner; **Hard** warns of the uncommitted changes it throws away. The reflog's **Reset** plans the reset in the graph too. The menus say **Merge into** instead of **Merge to**. In every preview the graph shows, the checked out commit's marker now moves where HEAD would be, instead of staying on the commit HEAD leaves.
- The banner of a rebase, cherry pick or revert planned in the graph is one row: its heading, the result (`6 commits → 4 (1 fixed up, 1 dropped)`) or the options, **Stash changes first** when there are uncommitted changes, and the buttons. - **Drag and drop in the graph**: drag a branch label onto another commit or branch to rebase it there, even a branch that isn't checked out, or onto the checked-out branch to merge it. Drag commits (or a selection) onto the checked-out branch to cherry-pick them. Each drop opens a menu of what it can do; a merge's dialog confirms, and a rebase or cherry pick is planned in the graph. Resting on a target previews the result in the graph, with the commits being moved highlighted and collapsed runs kept collapsed, and every change is animated.
- **Delete Worktree Folder...** in the graph's menu for another worktree's branch deletes that worktree after confirming. It stops instead while the worktree has uncommitted changes or untracked files.
- **Standalone app**: Show Log and Fetch in the file manager's right-click menu, as in TortoiseGit. Show Log on a file or folder shows its history.
- **Standalone app**: the **+** button (and **File > New Tab**) opens a New Tab dialog with your favorite and recent repositories. Type to filter, pin a repository to keep it in Favorites, or choose **Open Folder...** for any other.
- **Standalone app**: on Windows, the tab strip is the window's title bar, as on macOS, instead of sitting below a title bar and a menu bar. The window's buttons sit at its right end in the app's light or dark colors, and the menu opens from the button at its left, or with Alt or F10.
- **Standalone app**: after a few days of use, Sidereal asks once whether you'd star it on GitHub. **Help > Sidereal on GitHub** opens the repository, and after an update to a new minor version a message links to its release notes. The **About** section of Settings links to Sidereal's website, its repository, its Marketplace and Open VSX pages, the changelog and the new issue page.
- **Report an Issue** in the message asking for a rating, and in the standalone app's **Help** menu, opens the new issue page, as the command does, instead of the list of issues.
- The filter button opens the filter options in a panel over the graph, like the standalone app's Settings, instead of a bar above it. **Apply** and **Clear** close it.
- **Standalone app**: prompts, such as a new branch's name, have a close button that cancels them, like Escape. A list of choices shows its question above it instead of in a filter field, which only long lists of single choices have now.
- **Merge** asks in one dialog that lists the commits it brings in, with its options below them, instead of a series of prompts, in VS Code as in the standalone app. It shows whether it can fast-forward, and keeps **Don't commit** and the strategy options under **Advanced**. An option that doesn't apply with the others is turned off, its reason in its tooltip, and the dialog stays open while the view refreshes in the background.
- Every rebase is planned in the graph instead of a dialog: the graph shows the commits it replays where they will go, newest at the top, and a **Rebase** column slides out beside it with each commit's handle and action. They start all picked, ready to run as they are, or to drag into another order, reword, edit, squash, fix up or drop first (or press P, R, E, S, F or D), and the graph shows each change at once: a dropped or squashed commit loses its dot. A reworded or squashed commit's message is edited below its row. The banner above the graph, which stays in view as you scroll, says what the rebase does and holds **Change All to...**, **Rebase** and **Cancel**; Enter rebases and Escape cancels. It replaces the separate **Interactive Rebase** choice, and rebases a branch that isn't checked out too. **Ignore Date** is gone.
- While a rebase is under way, the graph keeps showing its commits the way it planned them, in the **Rebase** column: the commits made so far with a check, the one it stopped at (marked when on conflicts), and copies of those still to come on top. A step that made no commit of its own (skipped, or left with nothing to change) is named on the commit before it, and commits you make yourself at a stop, such as a commit split in two, stay in the band with that step. The banner shows how far it has got. For a cherry pick or revert of several commits, the banner lists those left. **Continue** (or **Resolve with AI...** while conflicts remain) stands out as the next step.
- **Cherry Pick** and **Revert** are planned in the graph instead of a dialog: the graph shows the commits they will add on top of the checked-out branch, and the banner above it, which stays in view as you scroll, says what they do and holds their options (**Record where it came from**, **Don't commit**, and for a merge commit the parent to apply it relative to) with **Cherry Pick** or **Revert** and **Cancel**. Enter starts it and Escape cancels. With **Don't commit**, the graph highlights the commits it applies instead. When the graph doesn't show the checked-out commit, the banner lists the commits.
- The buttons of the graph's dialogs can be reached with Tab and pressed with Enter or Space. In the merge dialog and the conflict overlay, Tab stays inside the dialog.
- The graph's SHA-1 column shows the first 8 characters of each hash instead of the full hash. Hover a hash to see it in full.
- **Standalone app**: releases no longer include the macOS and Windows zips. Download the `.dmg`, the `Sidereal-Setup` installer or the `.AppImage`.
- A rebase stopped on conflicts in a squash or fixup no longer says it stopped to edit the commit, and **Skip** asks about skipping the commit rather than its editing.
- A rebase whose plan was changed now drops a commit left with nothing to change, as one run as planned does, instead of stopping there. When the plan edits a commit, or squashes or fixes up commits, such a commit is kept (empty) instead, so the edit or the squash still applies to it rather than to the commit before it.
- When Sidereal fails unexpectedly while committing, merging, rebasing or cherry picking, the commit form's buttons work again afterwards, a dropped commit or branch no longer leaves its preview in the graph, and the Actions column keeps filling in as you scroll.
- A file's **Uncommitted** diff opened again after a commit compares with the new HEAD instead of the HEAD it was first opened with, and a conflict's **Ours ↔ Theirs** diff shows the current conflict's sides, not an earlier one's.
- A rebase being planned stays when a fetch in the background (VS Code's autofetch, a terminal) adds or prunes remote branches, or the graph refreshes, instead of losing the plan. It is cancelled when the checked-out branch or the local branches change.
- After `git submodule deinit` (or deleting a nested repository's `.git`), the folder left behind no longer hands its view state, such as its name, columns and issue linking, to the repository it is in, overwriting that one's.
- **Standalone app**: on Linux, **Open in Terminal** works without `x-terminal-emulator` (which only Debian and Ubuntu have): it tries `$TERMINAL`, then GNOME's, KDE's, Xfce's and other terminals, and xterm.
- **Standalone app**: tabs of repositories on a drive that isn't mounted when the app starts are no longer forgotten. They open again at a later start, once the drive is back.
- **Standalone app**: on Windows, a repository opened from **File > Open Repository** or by dropping its folder no longer opens a second tab when it is opened again another way, such as **Show Log** in Explorer, and is listed once in **Open Recent** and the New Tab dialog.
- **Standalone app**: binary files in a commit's details no longer show "+NaN −NaN" (and NaN in the totals), and no longer offer a diff that can't be shown.
- In VS Code, the graph picks up changes made outside VS Code as the standalone app does: Git commands run in a terminal, such as `git add` marking a conflict resolved, creating a branch or a tag or dropping a stash, and files changed by other programs. It no longer waits until you switch back to VS Code's window or press F5, and keeps refreshing in a repository with more than 10,000 changes.
- A change made right after another, such as a second `git add` a second after the first while the graph was still refreshing, or right after one of Sidereal's own actions, is no longer missed, leaving the graph showing a conflict already resolved.
- The graph no longer reloads after an install or a build writes more than 10,000 files into a folder Git ignores, such as `node_modules`.
- In a text field, such as the commit form's summary, Escape leaves the field instead of closing the commit details, and on macOS Ctrl+H deletes the character before the caret instead of jumping to HEAD.
- Switching repositories while the **Working tree changes** were loading no longer shows the previous repository's changes in the new one's details, where staging or committing would act on the wrong files.
- A commit that changes a file in a folder named `constructor`, `toString` or the like no longer leaves its details stuck on "Retrieving Commit Details ...". A branch of such a name no longer always counts as selected in **Manage Branches** (and so deleted with the selected ones), nor shows a worktree or upstream badge it doesn't have.
- Checking out a branch that was deleted meanwhile (in a terminal, say) no longer checks out the files of a folder of the same name instead, throwing away their uncommitted changes. It fails, saying the branch is gone.
- **Commit & Push** pushes to the branch's upstream only where `git push` would: a branch made from `origin/main` under another name no longer pushes its commits onto `main`, and a branch that pushes to another remote (`branch.<name>.pushRemote`, `remote.pushDefault`) no longer pushes to the one it fetches from. Sidereal asks where to push instead.
- A checked-out branch with a tag of the same name (a branch `v1` and a tag `v1`) is shown as checked out again in the References view, and named `v1` instead of `heads/v1` when an action stops on conflicts.
- Fetching a remote branch into a local branch, and pulling a remote branch, no longer take a tag of the same name on the remote instead (which left the branch's new commits unmerged and said "Already up to date").
- Deleting a branch on a remote no longer also deletes a tag of the same name there (or only the tag, once the branch is gone from the remote), and deleting a tag on a remote no longer deletes a branch of the same name.
- **Edit Remote...** no longer fails with "No such URL found" when the old URL has a character such as `+` or `?` in it, and removing a push URL no longer also removes the others that contain it.
- The **Sidereal** output log masks passwords and tokens in URLs, such as a remote's `https://user:token@host/repo.git`, so the log is safe to share in an issue.
- Sidereal uses the Git executable that `git.path` names after a restart too, instead of the one it used last, and switches to the one it finds itself once `git.path` is cleared.
- **Reset** (to a commit, or of the uncommitted changes) no longer starts on **Hard** because it was chosen last time, so one Enter can't throw away the uncommitted changes. It starts on **Mixed** instead.
- A repository without commits, such as one just created with `git init`, shows "This repository has no commits yet." in the graph instead of an error with a **Retry** that couldn't work. Its first commit shows up on its own.
- On an orphan branch (`git switch --orphan`), whose first commit isn't made yet, the graph shows the other branches' history instead of "Unable to Load Commits: fatal: bad revision 'HEAD'".
- **Standalone app**: a crash or a full disk while the app saves no longer empties its `state.json` or `settings.json`, which lost every tab, recent repository and setting. A file that can't be read is kept as `state.json.corrupt` (or `settings.json.corrupt`) instead of being overwritten.
- **Standalone app**: when something fails while the app starts, it says so and quits, instead of staying open (or running without a window) and ignoring every later **Show Log**, **Fetch** and `sidereal` request.
